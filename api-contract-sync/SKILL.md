# API 契约同步

## 概览

使用本技能让前端与后端通过项目内可追踪的 `.api` 目录保持同步。将 `.api` 视为接口交接层：后端变更负责写入契约，前端对接负责先读取契约再实现调用。

## 触发规则

任何涉及前后端通信的任务都必须调用本技能，不受语言、框架或通信协议限制。

典型场景：

- 新增或修改 HTTP 接口、GraphQL Resolver、RPC 方法、WebSocket 消息或 Controller Action。
- 创建或修改请求/响应模型、DTO、序列化器、校验器或生成式 API 客户端。
- 编写前端数据请求、表单提交、上传下载、鉴权、分页、错误处理等逻辑。
- 评审任何跨越前端/后端边界的代码。

## 目录约定

默认在项目根目录使用 `.api` 目录，除非仓库已有等价的接口契约目录。后端新增接口时，如果 `.api` 不存在，应同步创建。

推荐每个接口或方法一个契约文件：

```text
.api/
  auth-login.md
  users-create.md
  usb-password-update.md
```

文件名使用稳定的 kebab-case，并按业务域和动作命名。如果仓库已有命名约定，优先沿用。

## 后端工作流

创建或修改后端 API 时：

1. 先检查现有 `.api` 契约。
2. 按仓库既有模式实现或修改后端 API。
3. 在同一次变更中创建或更新对应的 `.api/*.md` 契约。
4. 写清楚前端可直接对接的调用方式、请求结构、返回值类型。
5. 同步记录校验规则、鉴权要求、错误结构和重要边界情况。
6. 确认没有旧 `.api` 契约与实际实现相矛盾。

## 前端工作流

对接后端 API 时：

1. 编码前先读取相关 `.api` 契约。
2. 如果契约不存在，先检查后端实现；无法安全推断时再要求补齐契约。
3. 按 `.api` 实现请求构造、客户端调用、响应解析和错误处理。
4. 语言支持类型时，尽量复用或生成与 `.api` 一致的请求/返回类型。
5. 如果发现实现与契约不一致，应更新 `.api` 或明确指出冲突，不要静默偏离。

## 契约模板

每个 `.api/*.md` 文件应简洁、具体，并足够让另一个 Agent 或前端开发者直接实现调用。

````markdown
# API：<业务域 动作>

## 摘要
- 用途：
- 后端文件：
- 状态：draft | active | deprecated

## 调用方式
- 方法/协议：
- 路径/Topic/Procedure：
- 鉴权：
- Content-Type：

## 请求
```ts
type Request = {
  // 字段、可选性、枚举、校验说明
}
```

## 成功响应
```ts
type Response = {
  // 成功数据结构
}
```

## 错误响应
```ts
type ErrorResponse = {
  // 错误包裹结构、错误码、错误消息
}
```

## 示例
```bash
curl ...
```

## 备注
- 分页：
- 幂等性：
- 限流：
- 副作用：
````

类型代码块可使用最适合项目的语言或格式：TypeScript、Dart、Go、PHP、Kotlin、Swift、JSON Schema、OpenAPI YAML 等。优先选择前端最容易消费的类型表示。

## 质量标准

- 不要只写模糊说明；必须包含具体字段、可选性和响应结构。
- 后端行为可查时，不要为前端凭空编造字段。
- 存在鉴权、Header、query/path/body 参数、上传下载时必须写明。
- 后端有统一响应包裹时，分别写清成功和错误包裹结构。
- API 行为变更必须与 `.api` 契约在同一次变更中同步。
- 如果项目已有生成客户端、校验器或测试，必须保持它们与 `.api` 一致。
